# Introduction
One of my key goals with the [LisaFPGA project](https://github.com/alexthecat123/LisaFPGA) was to provide a fully-integrated Lisa solution that included both hard disk and floppy disk emulation on the PCB. ProFile hard disk emulation was easy since I could just stick an ESP32-S3 on there and throw a slightly-modified version of my [ESProFile](https://github.com/alexthecat123/ESProFile) code onto it, but floppy emulation was a whole different matter. The only reliable Sony 3.5" floppy emulator out there (that I knew of) was the Floppy Emu, but it's closed-source and obviously couldn't be integrated into my board, so I had to come up with something else. Given that people could also just use an external floppy drive or external Floppy Emu, I stuck another ESP32-S3 on the board, along with an OLED and some control buttons, and released the board as-is with the floppy emulator functionality unimplemented.

## Features

But the wait is over; I've got it working now, and it's pretty darn cool! Here are all of the current features of the ESFloppy emulator (and some potential future enhancements too):
- Emulation of dual Twiggy drives for the Lisa 1; this is the only emulator capable of this as far as I'm aware
- Emulation of Sony 3.5" 400K and 800K disks, compatible with both Lisa and Mac
- Maybe I'll add 1.44MB and Apple ][ disk support in the future as well if there's enough interest (emphasis on MAYBE)
- Supports DC42 and raw images
- Unlike Floppy Emu, it actually updates the DC42 checksums when closing an image; the Floppy Emu wiping them out always REALLY bugged me. I'm probably the only person who cares about this one...
- Read, write, and format support all implemented
- Very small/cheap BOM; no extra CPLD or other support chips needed like on the Floppy Emu
- Standalone version coming soon; connect it to any Mac/Lisa instead of just your LisaFPGA

# Technical Details
If you just want to use ESFloppy and don't care about how it works, then don't bother reading this section!

I think the best way to explain how ESFloppy works is to compare/contrast it with how Floppy Emu works. A lot of my design decisions were attempts to optimize the Floppy Emu hardware around the much more capable ESP32, so that seems like a natural way to discuss things.

## How the Floppy Emu Works
The Floppy Emu design revolves around two main chips: an ATmega1284 microcontroller (think of it as somewhere in between the Arduino Uno's ATmega328 and the Arduino Mega's ATmega2560) and a Xilinx XC9572XL CPLD (basically a really tiny/pathetic FPGA). The microcontroller serves up the UI on the OLED and communicates with the SD card to read/write image data, but never actually reads or writes flux data. That's the job of the CPLD, which is programmed to receive 8-bit GCR-encoded values from the microcontroller over a parallel bus and send them out as flux transitions on the read data (RDA) line with the precise timing that's necessary. It also does the reverse: sensing flux transitions on the write data (WRD) line and converting them into 8-bit GCR values that are sent to the microcontroller over the same bus. There are also a few handshake and special-purpose communications signals between the CPLD and the microcontroller, but that's the gist of it.

In addition to handling the raw flux transitions, the CPLD also implements the drive's register-level interface. Sony 3.5" drives have a full register file that can be accessed by the host machine, and the CPLD monitors the register addressing and other control signals from the host computer and puts out the appropriate data automatically, offloading even more work from the microcontroller.

This division of labor allows a relatively slow microcontroller like the ATmega1284 to keep up with the incredibly time-sensitive task of sending out flux transitions precisely every microsecond; all it has to do is read a sector from the SD card and then send a byte of that sector to the CPLD. It can then go do whatever it wants while the CPLD sends out the data, after which the CPLD lets the 1284 know it's ready for more data and we give it another byte. Super easy, and it works the same way for writes just in reverse!

But what about the obvious bottleneck of SD card access speeds? SD cards, especially low-quality ones, can have long access times (especially during writes, which can sometimes spike up to 70 or more ms per track), and this is completely unacceptable in an environment where we need to be reloading the CPLD every 8 bits that it sends out. Well, it's actually not quite as hopeless as it initially sounds. While it is true that we can't miss a reload of the CPLD while we're in the middle of sending out a sector, we actually CAN miss a bunch (within reason) of reloads when in between sectors. A real GCR-encoded disk fills the inter-sector gap (the space between sectors) with a repeating "self-sync" pattern of ```FF 3F CF F3 FC FF```, and the floppy controller on the Mac/Lisa is perfectly fine with this; as long as it sees this pattern, it just assumes the disk hasn't spun around to the next sector yet. So if we need some time to load/store data to the SD card, we just wait until we're done with the current sector, start the SD card op, and then keep sending out this pattern until the op is done. Sure, this might result in an inter-sector gap that's waaayyy bigger than the gap on a real disk, but the only consequence of this is slightly slower access times. In fact, this self-sync behavior is built right into the CPLD; if the microcontroller fails to reload it when it requests a reload, it assumes that it's busy and starts sending out the sync pattern automatically.

Based on my (admittedly shallow) analysis of this particular aspect of its architecture, older versions of the Floppy Emu appeared to read/write the disk image a sector at a time, so every single time the disk spun from one sector to another, the SD card had to be accessed to load the next one and a bunch of self-sync would have to be inserted. I think this has been changed on later versions to read in and write out an entire track at a time though, which is a lot more efficient because now you only need to do one read/write per track instead of one read/write for every single sector in the track.

## How ESFloppy Works
ESFloppy does things a bit differently. Everything is done on an ESP32-S3 microcontroller; no CPLDs or other additional hardware is necessary, although we still implement a similar division of labor.

Thanks to the ESP32-S3's "blazing-fast" 240MHz clock, we're actually able to bit-bang flux transitions with the microsecond-level precision that's necessary. In fact, we even have time to execute dozens of lines of code BETWEEN every bit-bang, so the drive's full register file interface can get implemented and handled in between flux pulses. This is a little more difficult than I'm making it out to be, and gets harder on Twiggy because you have to emulate two drives simultaneously and have to output register data on a different pin than the flux data unlike Sony, but the general idea should be pretty clear.

But what happens if we need to read/write the SD card (or run the UI loop)? Well, now we've got a big problem that Floppy Emu didn't have. Remember, Floppy Emu's CPLD would automatically insert self-sync bytes whenever the microcontroller was off doing SD card stuff, but we aren't able to do that because if we're in the middle of an SD card op, our bit-banging logic will be blocked until the op is done! This will greatly confuse the host's floppy controller and everything will break. So what do we do?

Well luckily, the ESP32-S3 has not one, but TWO cores! So you can probably see where this is going: stick all of the time-sensitive bit-banging and interface logic on one core (the "interface core"), and put all of the SD card and UI logic on the other core (the "SD core"). Now, when the interface core needs to talk to the SD card, it just sends a request over to the SD core and waits for a response. Meanwhile, it can send out self-sync or do whatever else it needs to do. The SD core then sends the data back over whenever it's retrieved and encoded to GCR and the interface core can get to work again. The same thing can happen in the other direction too: when you insert a disk image in the UI, the SD core sends some data to the interface core specifying that a disk is inserted and its parameters, and if you request an eject, then the SD core forwards the request to the interface core and waits for an acknowledgement that it's complete.

So when you really think about it, we divided things in a very similar way to the Floppy Emu with it's microcontroller and CPLD with our interface core and SD core, with the interface core being the equivalent of the CPLD and the SD core being the equivalent of the microcontroller. The nice thing about our solution though is that the absence of the (no longer manufactured) CPLD lowers costs and makes things simpler. And thanks to the ESP32's faster clock and faster SPI hardware, SD card accesses are faster too, so reading/writing your emulated floppy feels faster than the Floppy Emu too.

Oh yeah, one other thing you may have always wondered about on Floppy Emu and that's present on ESFloppy too: why are there separate Mac 3.5" and Lisa 3.5" emulation modes? The Mac and Lisa use the same 3.5" Sony drive, right, so why do we need a different emulation mode for each one? Well, I didn't understand why either until I started working on this project, but it's because of the speed the Lisa expects disks to spin at versus the speed the Mac expects. For whatever reason, in every single speed zone, the Lisa spins the disk slightly faster than the Mac, and the TACH (tachometer) signal must reflect the proper speed or else the host system will keep trying to adjust the disk speed forever until it's perfect. As an emulator, we don't care about adjusting disk speed, so we just hard-code TACH to output the "perfect" speed that the floppy controller expects to see, but if that perfect speed is different on the Lisa than it is on the Mac, then we can't just hard-code a single value. And that's the whole reason why the Mac and Lisa 3.5" emulation modes exist; literally the only difference is that one of them outputs the Mac TACH speeds and the other outputs the Lisa TACH speeds. Pretty interesting, right?

# Installing/Upgrading the Firmware
There are three different ways to do this, and which one you choose comes down to whether you have a LisaFPGA or standalone ESFloppy and whether your ESFloppy has ever been programmed before.

## Option 1 - The easy LisaFPGA method; works on programmed and unprogrammed ESFloppies.
This one is simple; just clone the LisaFPGA repo and run the (program_board.sh)[https://github.com/alexthecat123/LisaFPGA#programmingupdating-the-firmware] script. This will automatically grab the latest ESFloppy firmware, build it, and install it onto your board, and also upgrade the ESProFile firmware and FPGA bitstream at the same time if applicable. Literally just one command, and it works regardless of whether your ESFloppy has already been programmed in the past or is fresh from the factory. But it DOES have to be on a LisaFPGA board; this obviously won't work with the standalone unit.

## Option 2 - The easy method that works with both LisaFPGA and standalone ESFloppies, but they must have already been programmed with an older firmware.
Download the [esfloppy_latest.bin](esfloppy_latest.bin) firmware file from this repo and copy it to the root of your microSD card. Insert the card into your ESFloppy and turn it on. You'll see a progress bar as the firmware upgrade commences. Once it's done, ESFloppy will reboot and tell you that the update succeeded. At this point you can delete the file from the card if you want, but you don't have to. As I said, this works on both the LisaFPGA and standalone versions of ESFloppy, but it must have already been programmed with an older version of the firmware in the past, or else it's incapable of scanning the SD card to upgrade to the new one.

## Option 3 - The hard(er) method that works with anything.
If neither of the above methods fit your situation, or you want to compile from source, then this is the method you'll want to choose. Start by downloading the Arduino IDE from [here](https://www.arduino.cc/en/software/) and install it onto your computer if you don't already have it.

Once you have it installed, download this repo and open the file [ESFloppy/ESFloppy.ino](ESFloppy/ESFloppy.ino) in the IDE. This will not only open that file, but will also automatically open all of the other source files at the same time. The IDE should now look about like this:

# Using It
Now let's talk about how to actually do something "productive" (as productive as anything floppy disk-related can be) with one of these things!

## Preparing an SD Card
First and foremost, make sure you're using a good-quality SD card. If you're not, then you might experience some weirdness from time to time (read/write operations failing in your OS, data corruption, and so on). I like [these 64GB PNY cards](https://www.amazon.com/dp/B0BF5XMJCM), but as long as it's good quality from a good brand, you should be fine.

Format your card as FAT32 and copy all of your disk image files over to it. Feel free to organize them into subdirectories if you'd like; that's all fully navicable in the file picker. ESFloppy supports both raw and DC42 images, with .dsk, .img, .image, and .dc42 extensions, for both Sony 3.5" and Twiggy emulation. Twiggy raw images don't actually exist as far as I know, but I added support for them anyway.

Obviously, make sure you insert the SD card into the ESFLOPPY SD slot on your LisaFPGA board (or the SD card slot on the upcoming standalone ESFloppy board) before trying to use the emulator. This paragraph shouldn't need to exist, but someone got mad at me over their LisaFPGA board not working because they somehow didn't realize that you had to turn the power switch on, so perhaps it needs to be said after all...

Adjusts the contrast (brightness) of the display in increments of 8, with a minimum of 8 and a max of 255. Pressing SEL while on this item highlights it for editing, and then you can use LEFT/RIGHT to increase/decrease the value. When you're done, press SEL again to finish editing.

Toggles the screen auto-dim feature on and off. If enabled, this feature will dim the display to 1/8 of the contrast setting after 30 seconds of inactivity to reduce OLED burn-in.

#### Save and Reboot
Commits any changes to these settings to non-volatile storage and reboots ESFloppy.

#### Discard and Reboot
Reboots ESFloppy, discarding any changes you may have made to the settings.

### Error Screens
There are several error screens that can pop up during use, but realistically there are probably only two that you'll ever see. You can dismiss any of these by pressing the SEL button. Actually, you can press any of the 3 buttons, but I only had room to fit "Press SEL" on the OLED!

#### Error: Image file is not contiguous!

MEOWMEOW picture

This means that your image file doesn't occupy a consecutive set of sectors on the SD card. It's annoying on the Floppy Emu whenever this happens, and it's annoying here too. Unfortunately I have to require contiguous images for the sake of speed, so there's no way around it. This is a common enough error that I made a whole [troubleshooting entry](#i-get-an-error-saying-that-my-image-file-is-not-contiguous-what-does-this-mean-and-how-do-i-fix-it) about it; go read that for a deeper explanation and the fix.

#### Error: Image already loaded in other drive!

MEOWMEOW picture

Unless something goes horribly wrong, you should only ever see this message in Twiggy mode. It'll pop up if you ever try to insert the same disk image into both drives, which obviously isn't allowed because letting two drives write to the same disk at the same time is a recipe for data corruption. Just dismiss the message and insert a different disk.

#### Any Other Error Message

If you get any other sort of error message, something probably went wrong when opening your disk image. ESFloppy does a bunch of checks on its images before even allowing them to be shown in the file picker to begin with, so theoretically these should never come up, but you never know. If you get any of them, it points to a corrupt/bad image. Or perhaps a bad assumption on my part somewhere deep within the code...


# Troubleshooting
Here are some common issues people encounter and their solutions. If you have a problem, read this before you go through the rest of the document!

## The emulator is really intermittent with disk reads/writes randomly failing and data getting corrupted. What's wrong?
Your SD card is probably flaky. Make sure you're using a good-quality SD card from a brand that people have actually heard of before. I buy [these 5-packs](https://www.amazon.com/dp/B0BF5XMJCM) of 64GB PNY cards a lot and they work great.

## I get an error saying that my image file is not contiguous. What does this mean and how do I fix it?
SD cards are split into 512-byte sectors, and ESFloppy and Floppy Emu require that each of your disk images be in a contiguous range of sectors. This is done for the sake of speed because it enables bypassing the filesystem once the image is open, but it also means that if the filesystem decides to write part of your image to one group of sectors and another part to another group somewhere else on the disk, then your image won't be contiguous and you'll see this error. This will probably only happen rarely, but if/when it does, the solution is normally to copy all of your files off the card, reformat it, and then copy them back onto it again. You can also experiment with deleting the offending file and copying it back into place, making a duplicate of the file and then deleting the original, or defragmenting the SD card.

## My image file doesn't show up in the file picker at all. Why?
The file picker does some image integrity checks while building its list of images and refuses to show anything that doesn't pass these checks. So if your image isn't showing up, then it's probably failing one or more of them. The checks are:

- Does the image name start with a "." character? If so, then it's probably supposed to be a hidden file, so don't show it.
- Does the image have a valid extension (.dsk, .img, .image, .dc42)? If not, don't show it.
- If the image is NOT a DC42, is its size valid for the current emulation mode (400K/800K size for Sony mode, Twiggy size for Twiggy mode)? If not, don't show it.
- If the image IS a DC42, does the image type in the header metadata match the current emulation mode? Do the data/tag field sizes in the header match the actual sizes of these fields in the file? Do these sizes match what we'd expect for an image in the current emulation mode? If the answer to any of these is no, then don't show it.

Note that these checks mean that Sony 3.5" images won't show up in Twiggy emulation mode, and Twiggy images won't show up in Sony mode. This is by design to reduce the amount of scrolling through useless images that you have to do; it's not a bug.
